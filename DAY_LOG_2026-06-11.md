## Render Build-Architektur Refactor

### Problem
Der erste Versuch Three-Layer-Shooting live zu bringen schlug fehl mit:
```
ERROR: Could not open requirements file: 'requirements.txt'
```

Diagnose: Beim Editieren des Render-Dashboard-Build-Commands ging das
Root-Directory-Setting verloren. Die 12-Step-Pipeline lebte als
800-Zeichen-String in einem UI-Feld — fehleranfällig, nicht versioniert,
nicht reviewbar.

### Lösung
**`backend/build.sh`** als Source-of-Truth für die Pipeline-Steps:
```bash
set -euo pipefail              # fail-fast bei jedem Fehler
cd "$(dirname "${BASH_SOURCE[0]}")"   # Working Directory robust
INJECT_STEPS=( 11 inject_*.py )       # explizite Reihenfolge
```

Mit Step-Headers im Output für lesbare Build-Logs:
```
============================================================
  STEP N/14: inject_X.py
============================================================
```

**`render.yaml`** im Repo-Root als Blueprint-ready Spec:
- Dokumentiert aktuelle Dashboard-Settings
- Bei Disaster-Recovery / Service-Neuerstellung direkt als Blueprint
  deploybar (Task #61 für mittelfristige Migration)

**`backend/render.yaml`** zu Deprecated-Stub reduziert mit Verweis auf
die neue Source-of-Truth.

### Architektur-Gewinn
| Vorher | Nachher |

| 800-Zeichen-Build-String im UI | 1 Zeile `bash build.sh` |
| Steps nicht versioniert | Steps versioniert, PR-reviewbar |

## Git-Index-Korruption — die unsichtbare Krise

### Symptom
Nach Dashboard-Refactor crashte der Build erneut, diesmal mit demselben
Error trotz korrekter Working Directory. Tieferer Look:

```
==> Downloaded 41KB in 0s
```

41 KB. Vorher beim 5f65521-Build waren es 43 MB.

### Diagnose
`git ls-tree -r origin/main --name-only` zeigte: **der Remote enthielt
nur 10 Files unter backend/**. Alle Backend-Python-Files
(`main.py`, `build_db.py`, `requirements.txt`, 11 `inject_*.py`), plus
komplettes Frontend, `.gitignore`, GitHub Actions — **nichts davon war
im Remote getrackt**.

Lokal waren die Files alle vorhanden, aber im Git-Index als "untracked"
ausgewiesen — d.h. ein vorheriger `git rm --cached -r` (vermutlich beim
Sprint-2 Recovery oder Mount-Korruption-Bug) hatte sie still aus dem
Index entfernt.

### Wie konnte das 6+ Tage unbemerkt bleiben?
**Render Build-Cache.** Der erfolgreiche 5f65521-Build hatte alle Files
gecached. Solange dieser Cache nicht invalidiert wurde, lief der Service
weiter ohne den Remote wirklich zu brauchen. Erst beim "Build cache
cleared" Trigger nach dem Dashboard-Edit wurde der Verlust sichtbar.

### Recovery — 4 Commits
| Commit | Inhalt | Größe |
|---|---|---|
| `7ced8b6` | 15 Backend-Python-Code-Files | 55 KiB |
| `88089ba` | 22 Configs + Frontend | 479 KiB |
| `481d95b` | 15 PBP-CSVs (shot_creation, mind_metrics, game_logs) | 29.9 MiB |
| `c92faae` | 4 BartTorvik-Raw-Files (37+38 MB) | 18.2 MiB |

Total: ~50 MB Push-Volume, ~1.27M Zeilen Code/Daten.

### Strategische Gewinn — indirekt
**Die Dashboard-Drift hat uns gerettet.** Ohne sie wäre der Render-Cache
weiter gelaufen und wir hätten die Index-Korruption erst beim nächsten
Disaster (Cache-Invalidierung, Service-Neuerstellung) bemerkt — möglicher-
weise Wochen später.

### Long-Term Hardening (Task #62)
GitHub Action die bei jedem Push verifiziert, ob critical Files
(`backend/main.py`, `requirements.txt`, `inject_*.py`, `App.jsx`) im
Remote vorhanden sind. Failt CI sonst.

## Comps-Endpoint Bug — SQLite-Wrapper-Iteration-Methoden

### Symptom
`/api/comps/anthro/cameron-boozer` → 500 Internal Server Error:
```
AttributeError: '_SqliteAnthroCompsDict' object has no attribute 'items'
```

### Root Cause
Beim Refactor von In-Memory-Dict zu SQLite-Lazy-Loading hatte
`_SqliteProfilesDict` (Z.302) die Iteration-Methoden bekommen
(`items`, `values`, `keys`). Für die Comps-Dicts wurde das vergessen.

`route_anthro_comps` (Z.969+976) macht aber `.items()` im Fallback-Pfad
(wenn kein pre-computed Comp-Eintrag existiert und live berechnet werden
muss).

### Fix
Iteration-Methoden in `_SqliteStatCompsDict` und `_SqliteAnthroCompsDict`
nachgezogen. Symmetrisch implementiert für beide Klassen,
zukunftssicher.

```python
def items(self):
    for row in _db().execute("SELECT player_id, data FROM anthro_comps"):
        yield row[0], (_decompress_blob(row[1]) or {})
```

Commit `31ebf4a`.

### Warnung im Code
Diese Iteration ist Full-Table-Scan über ~35k Entries — auf Free-Tier
5-30s Latency möglich. Kommentar im Code dokumentiert das. Long-term
sollte der Fallback-Pfad in einen eigenen Endpoint mit Index extrahiert
werden.

## Boozer-Position-Override (Task #11)

### Problem
Pipeline (`10c_ml_calibration.py`) klassifiziert Boozer als "Big" wegen
Anthro (78" + Power-Frame). Scout-Konsens und Skill-Profil
(Mid-Range-Tape, 22.6% self-created 3PA, FT-Mechanik, Movement) zeigen
Wing-Versatility.

### Lösung
**`backend/inject_position_overrides.py`** — neuer Pipeline-Step als
letztes vor Build-Validation. Manual Scout-driven Position-Fixes mit
dokumentierter Begründung pro Spieler.

```python
POSITION_OVERRIDES = {
    "bt:134971": {  # Cameron Boozer Duke 2026
        "pos": "Wing",
        "reason": "Wing-Versatility + Power-Wing-Frame; Pod 2026-06-04 Konsens",
    },
}
```

### Architektur-Eigenschaften
- **Collision-safe:** player_id-keyed (nicht name)
- **Audit Trail:** Pipeline-Original-pos bleibt als `pos_pipeline` erhalten
- **Reversibel:** Override entfernen + Re-Deploy → Pipeline-Position aktiv
- **Erweiterbar:** Neue Overrides einfach in Dict eintragen

### Wann diesen Override-Mechanismus benutzen
**Nur** für Edge-Cases mit klarer Scout-Begründung. Nicht als
Workaround für systematische Pipeline-Schwächen — diese gehören
ins 10c_ml_calibration gefixt. Der Override-Mechanismus ist für
echte 1-2-Spieler-pro-Klasse Hybriden gedacht.

Build.sh erweitert auf **14 Steps** (Position-Override als Step 14).

## Lessons Learned

1. **Render Build-Cache ist ein Sicherheitsrisiko.** Es kann einen
   broken Remote-State über Tage / Wochen kaschieren. Index-Drift-
   Detector als CI ist nicht optional.

2. **`git status` als Routinen-Check** schadet bei großen Repos nicht.
   Auch wenn man "nichts geändert" hat: ein `git status` zeigt, ob
   das Repo gesund ist.

3. **Settings als Code.** Wann immer eine Service-Config in einem
   UI-Feld lebt, ist sie ein latentes Drift-Risiko. `build.sh` +
   `render.yaml` sind die richtige Lösung — kostet 10 Minuten,
   spart Tage von Debug-Zeit.

4. **Mount-Korruption ist real.** WSL/FUSE-Mounts mit großen Files
   können stille Null-Byte-Tails produzieren oder Index-Korruption
   auslösen. Bei Pipeline-Re-Runs IMMER danach `git ls-tree -r
   origin/main` als Sanity-Check.

5. **Saubere Architektur zahlt sich aus.** Die Recovery war heute
   möglich weil der lokale Working Tree intakt war, weil die
   `.gitignore` clean war, weil das build-Script jetzt versioniert
   ist. Ohne diese Disziplin wäre die Recovery nicht möglich gewesen.
